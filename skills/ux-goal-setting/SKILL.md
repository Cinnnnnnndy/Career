# UX 设计目标制定

本 skill 提炼自 UCD 中心 2026 年 UX 设计项目目标制定研讨会（To B / To C / To D 三场、20+ 项目）的原始目标、SMART 刷新版、会上修改版和评委点评。用于：

- 从零写一个 UX 设计目标；
- 诊断已有目标（对照评委原则逐条挑问题）；
- 把“产品功能式”“口号式”目标改写成“设计策略 + 可测结果”式目标；
- 按项目场景切换写法（不同场景的侧重、指标和措辞不同）。

**铁律：不编造数据。** 基线、目标值、局点、版本、时间点缺失时，用 `【待补：xxx】` 标出，并在输出末尾列“待补数据清单”，不要自行填数字。

---

## 一、方法论：一条目标 = 五段链路

评委反复追问的其实是同一件事：**“做了什么设计 → 解决了什么问题 → 结果怎么衡量 → 在哪落地 → 支撑了什么”** 这条链路是否完整、可验证。

| 段 | 要回答的问题 | 写法要点 |
| --- | --- | --- |
| ① 场景与问题 | 哪类用户、哪几个场景、具体什么问题？现状多差？ | 场景要具像、划清边界（解决哪几类、哪几个问题）；现状用时间/步骤/成功率/口碑/感受量化；业务背景（如 VIP 问题）直接点明，不绕弯 |
| ② 设计策略与设计点 | 用什么**设计手段**解决？ | 写设计策略和设计点，不写产品功能；用“体验手段”语言（引导、可视、联动、渐进式简化、一站直达……） |
| ③ 体验结果 | 结果怎么测？从多少到多少？ | 指标与设计点一一对应；有基线、有目标值、可测试；用户感知型指标优先 |
| ④ 落地 | 何时、哪个版本、哪些局点/客户、何时验证？ | 落地时间与验证时间分开写；局点写具体，并确认这些局点都会做测评 |
| ⑤ 支撑业务 | 对业务目标的贡献？卖点、专利、规范沉淀？ | “支撑/助力”业务目标，“达成”自己的体验目标；卖点写清 X+ 个、在哪个大会/发布会发布 |

一句话骨架：

> 在【时间】前，聚焦【用户·场景】中的【问题（现状基线）】，通过【设计点 A / B / C】等设计策略，打造【体验关键词】体验，【版本】落地【局点】，【验证时间】前达成【指标：基线 → 目标】；【N+】设计点在【大会】发布形成卖点，支撑【业务目标】。

## 二、评委反复强调的原则（14 条）

1. **聚焦设计策略，不写产品功能目标。** “上线 8 个页面”“完成功能合并”“保障版本交付”“完成 xx 特性 UX 设计”是产品/交付目标，不是体验目标；要写“通过什么设计让用户体验发生什么变化”。
2. **设计点描述要设计化。** “新增极简模式”偏功能；“通过信息分级与极简模式，让 8.8 寸仪表一眼可读”才是设计化。参见第四节“功能化 → 设计化”对照。
3. **链路完整。** 做了什么（设计）+ 研发/业务助益 + 体验量化（提效、降错、满意度），三者都要有。
4. **有基线，从 X 到 Y。** “提升 20%”必须有基线测试数据；没有基线时先写“0→1 建立基线”的举措。
5. **指标细颗粒、与设计点绑定。** 不要只写笼统的“满意度提升 xx”，要有如“定位耗时从 1.5h 缩短到 0.5h”“安装部署从 1h 降到 30min 以内、成功率 100%”这类任务级指标。
6. **用户感知型指标优先。** 去掉“步数/点击次数”这类过程指标作主指标，改为任务时长、效率提升、成功率、VOC 声量等用户能感知的结果（步数可作辅助）。
7. **满意度统一 NSS 口径。** 不混用“满意度 80 分 / NPS / 评分 4.3”，统一写 NSS（必要时注明“单项 NSS”），并写清基线。
8. **指标可测试，带时间跨度。** PV/UV 写“上线 2 个月内”；耗时变化要确认能测；评估方式写清（可用性测试、年度 NSS 调研、VOC 统计）。
9. **写清时间点，落地与验证分开。** 版本上线后验证测试通常还需 1~2 个月，“7 月 15 日落地 26.1.0，9 月 15 日前验证达成 xx”；多里程碑用 630 / 930 / 1230 标在各子目标前。
10. **写清局点，并确认都会测评。** 局点/客户写具体；列了多个局点就要确认每个都会做满意度测评，做不到就只写会测的。
11. **“支撑”与“达成”分清。** 支撑/助力 = 辅助业务目标（商用发布、收入、生态、用户数）；达成 = 自己负责的体验目标（NSS、效率、成功率）。
12. **只承诺 UX 能影响的维度。** 付费比例、报告质量、收入等不是 UX 的直接结果，目标应落在 UX 能解决的维度（如“研究过程可视可控”“排版美观度单项 NSS”）。
13. **分段写，不混成一段。** 不同业务场景/方向/工具分开描述；**交付沿途落地**与**创新探索**分开写；创新部分写清营销展会和落地版本。
14. **句式精简，连词通顺。** 删重复语句（同一事实不说两遍）；注意“通过……，解决……，实现……，支撑……”的连接逻辑。

另外三条会上提到的补充：
- **指标互锁**：与产品线、研发对齐并达成共识后再定稿；可增加“0 号客户无负向投诉”这类产品线认可的指标。
- **竞品对标细化**：不写“体验领先竞品”，而写对标的具体维度（配置效率、可视化、告警交互……）。
- **业务目标变更要同步**：项目业务目标变了，UX 目标及时刷新。

## 三、按项目场景调整

先判断场景（可多选），再按对应要点写。不同场景的**侧重、指标和语料**不同。

### 3.1 按用户类型

| 类型 | 典型项目 | 问题侧重 | 推荐指标 | 设计点语料 |
| --- | --- | --- | --- | --- |
| **To B**（运营商/企业运维、控制台、管理平台） | 网管、云控制台、企业办公、能源管理 | 流程长、耗时久、依赖经验、信息难找、配置复杂 | 关键任务耗时（如 1.5h→0.5h）、任务成功率、查找耗时、VOC 负面声量、局点 NSS | 执行操作主动引导 / 执行过程直观可视 / 执行结果明确可控；一屏直达；操作零跳转；入口显性化、个性场景化、智能引导化 |
| **To C**（终端、车机、穿戴、云服务 App） | 新形态、主题美学、仪表、AI 助手 | 差异化不足、情绪价值、易读性、VIP 问题 | NSS（挑战值/底线值）、使用率/留存率、VOC 改善、卖点数、专利数 | 外屏有温度 & 内屏有深度；高效、沉浸、智慧；伴随式智能；一步灵动 |
| **To D**（开发者工具、IDE、开发者官网、芯片 EDA） | IDE、调优工具、开发者平台 | 上手难、迁移断层、定位难、工作流割裂 | 任务耗时（安装部署、问题定位）、成功率、效率提升（需基线）、VOC 降低、工具 NSS、自主闭环率 | 分角色任务引导；知识进工具；图表联动；观测模式；软硬一体可视化链路；导入牵引校验 |

### 3.2 按项目性质

| 性质 | 写法侧重 | 易犯错 | 句式提示 |
| --- | --- | --- | --- |
| **首版本 / 0→1** | 没有基线时，先写“建立基线”的举措，再给首测目标；强调体验框架/范式的建立 | 硬写“提升 xx%”却无基线 | “0→1 构建满意度采集渠道并划定基线，首版本 NSS 达 xx” |
| **重大改版** | 用现状数据（VOC、NSS、耗时）证明问题，再给前后对比 | 罗列改了哪些模块 | “将传统 xx 模式重塑为 xx 体验范式，NSS 从 a 提升至 b” |
| **日常迭代 / 维护** | 不要只写“版本迭代与维护”；挑 1~2 个高频 VOC 问题做核心体验点，其余写“保障体验问题 100% 闭环” | 目标只有“支撑版本交付” | “基于 VOC 高频反馈（a、b），完成 xx 与 xx 两项体验优化，NSS 底线 x、挑战 y” |
| **创新探索 / 预研** | 与交付沿途分开写；写清概念方案在哪个展会/大会亮相、最终落入哪个版本、专利数 | 创新与交付混写，无落地出口 | “概念方案支撑【展会】展示，最终设计方案落入【版本】；形成【N】项专利” |
| **AI / Agent 智能化** | 写清 AI 解决的具体任务，以及可信、可控、可视的设计策略；指标落在任务成功率、自主闭环率、过程可视 | 写“AI 能力提升”这类技术目标；把模型效果当 UX 结果 | “通过过程可视可控、意图确认、分级输出等设计，典型任务成功率 ≥ x%，咨询类问题自主闭环率 a%→b%” |
| **平台 / 规范沉淀** | 作为附加产出写：设计规范、组件/模板复用、范式赋能其他服务 | 当成主目标 | “沉淀 xx 规范 2.0 / 极简版范式，赋能 N 个基础服务” |
| **内容型站点 / 官网** | 区分产品目标（上线页面数）和体验目标（找到所需内容的耗时、学习路径完成率） | 用“上线 x 个页面、PV 4w+”当体验目标 | “PV/UV 写时间跨度；体验指标写找到目标内容耗时环比缩短 xx” |

### 3.3 多工具/多方向项目

一个项目覆盖多个工具或方向（如 IDE + CLI + 插件；四大特性方向）时：先写一段**整体体验目标**（总 NSS、总效率），再**每个方向单独一段**，各自写问题→设计点→指标。不要把四个方向的指标挤在一句里。

## 四、表述方式（语料）

### 4.1 标准模板（单一场景）

```
在【YYYY 年 M 月 D 日】前，聚焦【用户角色】在【场景 1/2/3】中【问题：现状量化】的核心问题，
通过【设计点 A】、【设计点 B】、【设计点 C】等体验设计策略，打造【关键词1、关键词2、关键词3】的【xx】体验，
于【版本】落地【局点/客户】，【验证日期】前达成【指标1：基线→目标】、【指标2】、【NSS：基线→目标】；
【N+】设计点在【大会/发布会】发布形成卖点，形成【N+】专利，支撑【业务目标】。
```

### 4.2 多场景分段模板

```
【整体】在【时间】前，围绕【业务方向】，打造【体验关键词】的端到端体验，达成整体 NSS 从 a 提升至 b，支撑【业务目标】。

【场景/方向 1：名称】针对【问题 + 现状】，通过【设计点】，实现【任务指标：基线→目标】，【时间/版本】落地【局点】。
【场景/方向 2：名称】……
```

### 4.3 交付沿途 + 创新分开模板

```
一、交付沿途落地
在【时间】前，围绕【版本/特性】，通过【设计点】，解决【问题】，落地【版本】，达成【NSS/任务指标】，体验问题 100% 闭环。

二、创新探索
围绕【新形态/新方向】，探索【设计方向】，完成【概念方案】，在【展会/大会】发布，最终落入【版本】，形成【N+】高价值体验卖点、【N+】专利。
```

### 4.4 SMART 展开（评审要求时才用）

只在需要时附 SMART 拆解，且**不要与主目标重复**：S 写场景与设计点，M 写指标与评估方式，A 写基线来源与资源，R 写与业务战略的关系，T 写里程碑（630/930/1230）。主目标一段已讲清时，SMART 只补主目标没讲的内容。

### 4.5 常用动词与连接

- 开头：在……前 / 聚焦…… / 围绕…… / 针对……
- 手段：通过……设计 / 以……为支点 / 基于……
- 产出：打造……体验 / 构建……范式 / 重塑为…… / 形成……卖点
- 结果：解决……问题 / 实现…… / 达成……（自己的目标）
- 落地：落地【版本】/ 在【局点】试点 / 随【版本】上线
- 业务：支撑……（业务目标）/ 助力……达成（生态、商用、发布）

### 4.6 设计点“三连”表述（会上认可的写法）

- 执行操作**主动引导**、执行过程**直观可视**、执行结果**明确可控**
- 入口**显性化**、个性**场景化**、智能**引导化**
- **极简选配**、**一键迁移**、**无感升级**
- 一屏直达关键信息、操作零跳转、常用操作一步直达
- 高效、沉浸、智慧的会议协同体验
- 复杂数据的直观表达与极简洞察
- 从“人找信息”到“信息找人”

### 4.7 功能化 → 设计化 对照

| 偏功能（避免） | 设计化（推荐） |
| --- | --- |
| 新增极简模式 | 通过信息分级与极简模式设计，让小尺寸仪表关键信息一眼可读 |
| 完成“此刻”“源网荷储拆分”特性 UX 设计 | 通过自然语言状态描述（此刻）、清晰的能源来源去向分解（源网荷储拆分），实现复杂数据的直观表达与极简洞察 |
| 合并两个管理平台的功能 | 以统一入口、全流程闭环的信息架构，消除应用上架在两个平台间的跳转割裂 |
| 上线 8 个场景化页面 | 以场景化学习路径重组分散的开发知识，缩短开发者找到所需内容的时间 |
| 完成 AI 对话割接流程 | 通过人机对话的主动引导与过程可视，让割接操作不再依赖人工经验 |
| 优化 timeline 易用性 | 通过图表联动与 4 类观测模式，降低 Timeline 异常特征的辨识成本 |
| 多 Agent 管理页面设计 | 以多智能体全景视图作为统一入口，让用户快速掌握各 Agent 运行状态 |

### 4.8 避免的写法

- “提升用户体验”“打造极致体验”“体验领先竞品”——无对象、无指标。
- “保障版本有序、高质量交付”作为主目标——是交付职责。
- 只写满意度，不写任务级指标。
- 同一指标在主目标和 SMART 里各写一遍。
- 混用满意度 80 分 / NPS / NSS / 4.3 分。
- “支撑达成用户满意度 ≥ 80”——自己的目标用“达成”，不用“支撑”。

## 五、写作步骤

1. **收集输入**：业务目标、版本与时间、目标用户、局点/客户、现状数据（NSS、VOC、任务耗时、成功率）、已规划的设计点、对外发布节点（大会/展会）、专利计划。
2. **判断场景**：按第三节确定用户类型 + 项目性质（可多选），确定是否需要分段、是否拆“交付沿途 / 创新”。
3. **列问题清单**：每个场景 1~3 个核心问题，写现状（时间、步骤、成功率、口碑、感受）。
4. **问题 → 设计点 → 指标 一一对应**：每个设计点对应它解决的问题和能测出来的指标；没有对应指标的设计点要么补指标，要么降级为举措。
5. **定基线和目标值**：有数据写“从 a 到 b”；没数据写“0→1 建立基线”并标【待补】。确认指标可测、口径为 NSS、带时间跨度。
6. **定时间和局点**：落地时间、验证时间、里程碑（630/930/1230）；局点具体且会测评。
7. **写业务支撑**：卖点数量与发布场合、专利、规范沉淀；用“支撑/助力”连接业务目标。
8. **套模板成文**，再精简：删重复、理连词，单段控制在 150~250 字左右。
9. **跑自检清单**，列待补数据。

## 六、自检清单

- [ ] 写的是设计策略/设计点，不是产品功能或交付动作
- [ ] 设计点用的是体验手段语言（设计化），不是功能名
- [ ] 场景具体、问题边界清楚（解决哪几类、哪几个问题）
- [ ] 每个关键指标都有基线和目标值（从 X 到 Y）
- [ ] 有和设计点绑定的任务级指标，不只是笼统满意度
- [ ] 主指标是用户感知型（时长、效率、成功率、VOC），不是步数
- [ ] 满意度统一 NSS 口径，写清基线；评估方式写清
- [ ] PV/UV 等指标带时间跨度；每个指标都能测
- [ ] 有截止时间；落地时间与验证时间分开
- [ ] 局点/客户具体，且都会做测评
- [ ] “支撑”用于业务目标，“达成”用于自己的目标
- [ ] 只承诺 UX 能影响的维度（不把付费、收入当 UX 结果）
- [ ] 多场景/多工具分段；交付沿途与创新分开；创新写清展会与落地版本
- [ ] 卖点写清数量与发布场合；专利/规范为附加产出
- [ ] 指标已与产品线、研发对齐（或标注待对齐）
- [ ] 无重复语句，连词通顺，无空话

## 七、范例（脱敏，原始 → 评委点评 → 改写）

### 范例 1 · To B · 运维效率型（AI 对话完成光缆割接）

**原始**：针对光缆割接场景，设计并落地 AI 对话完成割接准备、实施监控、异常处理、总结反馈等端到端流程，提升割接操作工作效率，降低运维人员技术门槛。用户满意度达 80 分以上。关键局点：A 移动、B 移动、C 移动。

**评委点评**：目标要体现设计策略是什么，而不只是业务能力提升；割接前后阶段耗时变化是否可测试；列出的局点是否都会做满意度测评。

**改写**：在 2027 年 4 月 30 日前，聚焦运营商 TOP 光缆割接场景，通过灵活、高效、自然的人机对话方式，打造执行操作主动引导、执行过程直观可视、执行结果明确可控的割接体验，解决传统割接流程长、耗时久、依赖人工经验的问题；割接前准备与割接后质量确认耗时从 1.5h 缩短至 0.5h【待确认可测】，26B 版本落地 B 移动局点，用户体验 NSS 达 80 及以上。

**要点**：设计策略“三连”、只保留确定会测评的局点、耗时指标先确认可测。

### 范例 2 · To D · 开发者工具 / 调优型（性能调优可视化工具）

**原始**：聚焦模型训推调优场景，针对“性能瓶颈定位难”，通过多维度数据可视化 + 系统建议，提升定位与解决效率，实现满意度达成 80 分基线，3+ 关键任务效率提升 20%。

**评委点评**：上线后验证还需 1~2 个月，达成满意度要另写时间点；语句重复需精简；支撑/达成要分清；“耗时缩短 20%+”需要基线测试数据。

**改写**：聚焦模型训/推性能调优中“内存诊断——异常内存定位耗时长”“Timeline 性能诊断——异常辨识成本高”“工程管理——落盘文件导入与区分易出错”三大场景，通过图表联动、Timeline 4 类观测模式、落盘文件导入牵引校验等体验方案专项解决，于 2026 年 7 月 15 日前落地 26.1.0 版本供核心客户使用，9 月 15 日前验证达成 NSS ≥ 80、内存与 Timeline 定位作业耗时缩短 20%+（基线：【待补】）、工程文件管理 VOC 降低 50%。

**要点**：“场景——问题”成对写；落地与验证两个时间点；自己的指标用“达成”。

### 范例 3 · To D · 首版本 IDE + 创新（BMC 开发 IDE）

**原始**：聚焦整机与部件厂商端到端开发及从旧工具迁移场景，通过一站式体验架构、欢迎页 & 分角色任务引导、模型检查 & 故障上报、软硬一体可视化链路、“知识进工具”分层辅助等设计点，解决工具迁移断层、新用户上手难、工作流不连贯问题，保障体验问题 100% 闭环，落地 MVP、930、年底易用等版本及 6 家厂商验证局点，大会形成卖点视频助力 IDE 发布。

**评委点评**：增加具体基线数值，写出 X+ 设计点形成卖点发布；对问题和目标定量定性（时间、步骤、口碑、感受），如上手困难用户形成多少正向口碑；增加创新和平台目标（创新点高品质落地与满意度、软硬协同系统化设计）。

**改写**：聚焦整机与部件厂商端到端开发场景，通过一站式体验架构、欢迎页 & 分角色任务引导、模型检查 & 故障上报、软硬一体可视化链路、“知识进工具”分层辅助等 5+ 核心设计点，解决安装部署成功率低耗时长跳转多、配置规则复杂问题定位难、软硬件视图割裂等问题，保障开发者无缝迁移工具。实现：安装部署时长由 1h 降至 30min 以下、成功率 100%；CSR 拓扑配置效率提升 15%；体验问题 100% 闭环；3+ 设计点在开发者大会发布形成卖点；保障 630 MVP、930、1230 易用版本发布，NSS 达 52%（挑战 55%），助力开源生态建设目标达成。
**创新探索（建议单列）**：探索 AI 辅助开发与软硬协同可视化，形成硬件开发软硬协同系统化设计模式，创新点首测 NSS【待补】。

**要点**：问题写成可量化现状；指标逐条列；创新与交付拆开。

### 范例 4 · To D · 内容型官网（产品目标 vs 体验目标）

**原始**：首版本大会前上线 8 个场景化页面（规划 13 个），平均页面 PV 挑战 4w+。

**评委点评**：PV/UV 要有时间跨度；不要把“上线 x 个页面”这类产品目标当体验目标；要有与设计点紧密结合的量化体验指标（如操作路径耗时环比缩短 xx），而不是笼统满意度。

**改写**：在开发者大会前，聚焦热门场景，以场景化学习路径重组分散、层级深的开发知识，解决开发者学习上手找不到、看不懂的问题；首版本 8 个场景页上线后 2 个月内平均 PV/UV 4w+，开发者找到目标内容的路径耗时环比缩短【待补】%，支撑“增加生态共建者”战略。

**要点**：页面数作为交付背景，体验指标落在“找到内容”的耗时。

### 范例 5 · To C · AI 助手（UX 能影响的维度 + NSS 口径）

**原始**：围绕深度研究拓展用户群和提升付费比例的业务目标，完成研究报告生成全链路优化设计方案，用户满意度从 70 分达到 80 分。

**评委点评**：“付费/报告质量”与 UX 设计的因果关系要理清，目标聚焦 UX 能解决的维度；满意度统一用 NSS。

**改写**：在 2026 年 12 月 31 日前，围绕深度研究 Agent 拓展客群与付费提升的业务目标，聚焦“研究过程黑盒”与“PPT 报告美观度低”两大体验痛点，完成研究过程可视可控方案与报告生成模板设计，落地 PC 及手机端 7.0 版本并在新品发布会发布；PPT 报告排版与视觉美观度单项 NSS 从 45% 提升至 60%，沉淀的报告质量能力横向复用到文档助手等场景。

**要点**：业务目标作背景，承诺只落在“过程可视、排版美观”这类 UX 维度。

### 范例 6 · To C · 迭代维护型（从空泛到具体）

## 八、输出格式

当用户给出一段已有目标请求诊断/改写时，按以下结构输出：

1. **场景判断**：用户类型 + 项目性质（一行）。
2. **问题诊断**：对照第二节原则和第六节清单，列出命中的问题（最多 6 条，按影响排序）。
3. **改写版目标**：按对应模板成文；需要时分“整体 / 各方向”或“交付沿途 / 创新”。
4. **待补数据清单**：所有 `【待补】` 项，说明该向谁要（产品线、研发、数据平台、用户研究）。
5. （可选）**精简版**：一句话 80 字以内版本，用于 PPT 标题页。

当用户从零开始写时，先按第五节第 1 步逐项询问缺的输入（一次问完），能推断的先按最可能的情况写，并标注假设。
